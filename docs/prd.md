## 1. 배경 및 문제 정의

현재 저장소에는 `frontend/` 디렉터리만 존재하며, ToDo 데이터는 `App.tsx`의 React 상태(`useState`)로만
관리된다. 따라서 페이지를 새로고침하거나 다른 기기로 접속하면 모든 ToDo가 사라지고, 사용자를 구분하는
개념 자체가 없다. [README.md](../README.md)에는 FastAPI 백엔드와 Supabase(PostgreSQL + Auth)를 추가해
데이터 영속성과 사용자 인증을 확보하는 목표 아키텍처가 정의되어 있으나 아직 구현되지 않았다.

이 PRD는 **(a) 이미 구현된 프론트엔드 CRUD/접근성 동작을 회귀 없이 보존**하면서, **(b) Backend API와
DB를 추가해 로그인한 사용자별로 ToDo를 영속적으로 저장**하는 것을 목표로 요구사항을 정의한다.

## 2. 현재 상태 → 목표 상태 Gap 요약

| 영역 | 현재 상태 | 목표 상태 | 관련 요구사항 |
| --- | --- | --- | --- |
| 데이터 저장 | React 상태, 새로고침 시 소실 | Supabase PostgreSQL에 영속 저장 | FR-009 |
| 사용자 구분 | 없음(단일 익명 세션) | Supabase Auth 기반 로그인 사용자별 데이터 격리 | FR-007, FR-008 |
| API 계층 | 없음(프론트 내부 상태 함수 호출) | FastAPI REST API 경유 | FR-001~FR-006, API 명세 전체 |
| 입력 검증 | 프론트 `trim()` 빈 값만 차단 | 서버 측 검증(길이, 공백, 인증) 추가 | FR-010 |
| 배포 | 없음 | Vercel(프론트 정적 호스팅 + FastAPI 서버리스) | NFR-005 |
| 접근성/반응형 | 구현됨 (`TodoItem`, `ProgressMeter`, `index.css`) | 동일 동작을 API 연동 후에도 유지 | NFR-001, NFR-002 |

## 3. 요구사항 ID 체계

- `FR-xxx`: 기능 요구사항(Functional Requirement). 사용자가 직접 수행하거나 체감하는 기능.
- `NFR-xxx`: 비기능 요구사항(Non-Functional Requirement). 성능, 보안, 접근성, 배포 등 품질 속성.
- 모든 하위 문서(API 명세, DB 스키마, 수용 기준, TASKS)는 해당 요구사항 ID를 **그대로 인용**하여
  추적성을 유지한다. 새 요구사항이 생기면 이 표에 먼저 추가한 뒤 하위 문서에 반영한다.

## 4. 범위

### 4-1. In-scope (이번 PRD 대상)

- ToDo 항목의 생성/조회/수정/삭제/완료토글 (CRUD) — API 및 DB 영속화 포함
- Supabase Auth 기반 로그인/로그아웃 및 사용자별 데이터 격리
- 완료율(ProgressMeter) 표시를 서버에서 받은 데이터 기준으로 유지
- 기존 접근성(키보드 포커스, aria-live, 체크박스 네이티브 요소) 및 반응형(360px 기준) 동작 보존
- FastAPI 입력 검증 및 에러 응답 표준화
- Vercel 배포 설정(프론트/백엔드)

### 4-2. Out-of-scope (이번 PRD 비대상)

- 회원가입 시 이메일 인증/소셜 로그인 등 Auth 세부 전략 선택(별도 ADR 필요, 본 문서는 "로그인된 사용자"
  존재만 전제)
- ToDo 공유, 협업(다중 사용자 공동 편집), 태그/우선순위/마감일 등 신규 데이터 필드 확장
- 오프라인 지원, 실시간 동기화(Supabase Realtime)
- 알림(이메일/푸시)
- 페이지네이션, 검색, 사용자 지정 정렬(드래그 등) — 목록은 항상 "생성일 오름차순" 전체 조회로 고정

## 5. 사용자 페르소나 및 스토리

**페르소나**: 개인 할 일을 웹에서 빠르게 기록하고 관리하려는 로그인 사용자 1명(개인용 ToDo, 협업 없음).

| ID | 사용자 스토리 |
| --- | --- |
| US-1 | 사용자로서, 로그인 후 내 할 일 목록을 어떤 기기에서 접속해도 동일하게 보고 싶다. (FR-007, FR-008, FR-009) |
| US-2 | 사용자로서, 할 일을 입력하고 추가 버튼을 누르면 목록에 즉시 반영되길 원한다. (FR-001) |
| US-3 | 사용자로서, 체크박스를 눌러 완료 여부를 바로 전환하고 싶다. (FR-003) |
| US-4 | 사용자로서, 기존 할 일의 텍스트를 수정하거나 실수로 수정 모드에 들어가면 Esc로 취소하고 싶다. (FR-004) |
| US-5 | 사용자로서, 더 이상 필요 없는 할 일을 삭제하고 싶다. (FR-005) |
| US-6 | 사용자로서, 전체 할 일 중 몇 %를 완료했는지 한눈에 보고 싶다. (FR-006) |
| US-7 | 키보드/스크린리더 사용자로서, 마우스 없이도 모든 CRUD 동작과 포커스 흐름을 이용할 수 있어야 한다. (NFR-001) |

## 6. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| **FR-001** | 사용자는 텍스트를 입력해 새 ToDo를 생성할 수 있다. 공백만 있는 입력은 거부한다. | 기존 `TodoInput`/`addTodo` 동작 유지 |
| **FR-002** | 사용자는 로그인 상태에서 본인 소유의 ToDo 목록을 생성일 오름차순(기존 배열 추가 순서와 동일)으로 조회할 수 있다. | 목록 조회 API 신설 |
| **FR-003** | 사용자는 개별 ToDo의 완료 상태를 체크박스로 토글할 수 있다. | 기존 `toggleTodo` 동작 유지 |
| **FR-004** | 사용자는 개별 ToDo의 텍스트를 인라인 편집 후 저장하거나 취소할 수 있다. 저장 시 공백만 있는 값은 거부한다. | 기존 `TodoItem` 편집 UI 유지 |
| **FR-005** | 사용자는 개별 ToDo를 삭제할 수 있다. | 기존 `deleteTodo` 동작 유지 |
| **FR-006** | 시스템은 전체 ToDo 수 대비 완료 개수/비율을 계산해 표시한다. | 기존 `ProgressMeter` 계산 로직(24개 이하 세그먼트, 초과 시 막대) 유지, 서버 응답 데이터를 입력으로 사용 |
| **FR-007** | 사용자는 Supabase Auth를 통해 로그인/로그아웃할 수 있어야 하며, 비로그인 상태에서는 ToDo API를 호출할 수 없다. | FastAPI는 로그인 처리를 직접 하지 않고 Supabase 발급 JWT를 검증만 수행 |
| **FR-008** | 모든 ToDo 데이터는 소유자(user_id)로 격리되어, 본인 소유가 아닌 ToDo는 조회/수정/삭제할 수 없다. | DB RLS + API 인가 이중 적용 |
| **FR-009** | 생성/수정/삭제/완료토글 결과는 Supabase PostgreSQL에 즉시 영속 저장되어 새로고침 후에도 유지된다. | 핵심 Gap 해소 항목 |
| **FR-010** | 서버는 ToDo 텍스트에 대해 공백 제거 후 빈 문자열 및 최대 길이 초과(500자) 입력을 거부하고 명확한 에러를 반환한다. | 프론트 trim 검증을 서버에서도 재검증(신뢰 경계) |

## 7. 비기능 요구사항 (Non-Functional Requirements)

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| **NFR-001** | 접근성: 체크박스는 네이티브 `<input type="checkbox">` 유지, 각 ToDo 텍스트는 연결된 `<label>` 사용, 버튼은 할 일 내용을 포함한 `aria-label` 제공, 완료율 영역은 `aria-live`로 변경을 안내한다. | 현행 `TodoItem`, `ProgressMeter` 구현 보존 |
| **NFR-002** | 반응형: 화면 폭 360px 이상에서는 작업 버튼을 한 줄에 배치하고, 359px 이하에서는 버튼이 줄바꿈된다. | 현행 `index.css` 미디어쿼리(`max-width: 359px`) 보존 |
| **NFR-003** | 포커스 관리: 편집 저장/취소 후 포커스는 해당 항목의 "수정" 버튼으로, 삭제 후 포커스는 새 ToDo 입력창으로 복귀한다. | 현행 `returnFocus`, `inputRef` 로직 보존 |
| **NFR-004** | 보안: Supabase `service_role` 키는 백엔드 서버 환경에서만 사용하고 클라이언트/저장소에 노출하지 않는다. 모든 ToDo API는 Authorization 헤더의 JWT 검증을 통과해야 호출 가능하다. | README 환경변수 표 기준 |
| **NFR-005** | 배포: 프론트엔드는 Vercel 정적 호스팅, 백엔드는 Vercel 서버리스 함수로 배포 가능해야 한다. | README 배포 전략 기준 |
| **NFR-006** | 가용성/에러 처리: API 호출 실패(네트워크 오류, 인증 만료, 검증 실패) 시 사용자에게 피드백을 제공하고 로컬 상태를 서버 상태와 불일치시키지 않는다(낙관적 업데이트 시 롤백). | 신규 프론트 요구사항 |
| **NFR-007** | 성능: 목록 조회 API는 일반적인 개인 사용 규모(수백 건 이하)에서 체감 지연 없이(≤500ms, p95) 응답한다. | 목표치, 측정 방법은 TASKS에서 구체화 |

## 8. 성공 지표 (Success Metrics)

1. 새로고침/재로그인 후에도 ToDo 데이터가 100% 유지된다 (FR-009 충족 여부로 검증).
2. 사용자 A의 로그인 세션에서 사용자 B의 ToDo가 전혀 노출되지 않는다 (FR-008).
3. 기존 접근성/반응형 수용 기준(E2E 체크리스트)이 API 연동 이후에도 모두 통과한다 (NFR-001~003).
4. `npm run build`(타입 검사 포함) 및 `npm run lint`가 통과한다.
